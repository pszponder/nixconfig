# Architecture Refactor

## Goals

- Restore a minimal working NixOS configuration for `tpx1`, organized using the dendritic pattern.
- Remove Hjem and the `nix-wrapper-modules` dependency, including custom wrappers used to inject application configuration.
- Manage application dotfiles in [pszponder/dotfiles](https://github.com/pszponder/dotfiles) through Stow. Keep system configuration such as GNOME and the Kanata service and its configuration in Nix.
- Consolidate ordinary applications into package lists. Keep separate feature modules where they make system configuration easier to understand.
- Keep the structure extensible without implementing other platforms during this refactor. Future macOS support may use nix-darwin; Ubuntu support would cover Nix packages and development environments.

The immediate target is a working machine with a small, understandable configuration. Preserving every wrapper-provided convenience is outside the scope of this refactor.

## New file structure

Inspired by [Renato Garcia - A Simple Nix Dendritic Config](https://renatogarcia.blog.br/posts/a-simple-nix-dendritic-config.html)

```txt
- flake.nix
- modules/
  - parts.nix
  - base/
    - configuration.nix
    - packages.nix
  - hosts/
    - tpx1/
      - default.nix
      - hardware.nix
      - _hardware-configuration.nix
  - users/
    - piotr/
      - default.nix
  - features/
    - gnome.nix
    - ...
```

The directory tree follows a convention: either the file is named after the aspect (e.g., docker.nix) or the parent directory matches the aspect name. This is not a strict requirement, just a convenient way to organize the code.

### modules/

Most Nix files under `modules/` are Flake Parts modules, discovered by `import-tree`. Files prefixed with `_` are implementation details imported explicitly by their owning module.

Reusable aspects are defined under `flake.modules.<class>.<aspect>`, initially using the `nixos` class. Other Flake Parts modules define outputs such as packages and host configurations.

Aspect names include meaningful directory context: `base/configuration.nix` defines `baseConfiguration`, `base/packages.nix` defines `basePackages`, and `hosts/tpx1/hardware.nix` defines `tpx1Hardware`. A `default.nix` uses the aspect directory name, such as `gnome` or `tpx1`. Organizational directories such as `features` and `users` do not need prefixes: `docker`, `desktopPackages`, and `piotr` already identify their aspects clearly.

`parts.nix` imports `inputs.flake-parts.flakeModules.modules` and declares the systems currently supported. Discovering a module registers its definitions; hosts explicitly select which aspects to import.

### modules/base/

A small NixOS baseline and shared package lists. Ordinary applications do not need individual feature modules. Add overlays only when a concrete package customization requires them.

### `modules/hosts/<host_name>/`

Contains specific configuration for specified `<host_name>`

- `default.nix` constructs `nixosConfigurations.<host_name>`, selects base, hardware, user, and feature aspects, and contains host-specific configuration.
- `hardware.nix` is a module which imports `_hardware-configuration.nix`
- `_hardware-configuration.nix` is just a renamed `hardware-configuration.nix` generated by `sudo nixos-generate-config`

```sh
# How to generate only hardware-configuration.nix in specific location
sudo nixos-generate-config --show-hardware-config > ~/repos/github/pszponder/nixconfig/modules/hosts/tpx1/_hardware-configuration.nix
```

### modules/features/

A collection of Flake Parts modules for features such as GNOME, Docker, and Kanata. Each feature defines the NixOS aspect selected by a host.

### modules/users/

User account definitions, initially `piotr/default.nix`. Piotr is the main user on `tpx1`; this aspect includes `wheel`, `networkmanager`, and `docker` group memberships. A generic multi-user abstraction is not needed for this refactor.

## Plan

1. Consolidate ordinary applications into package lists.
2. Ensure replacement application configuration is available in the dotfiles repo, then remove Hjem and custom wrappers. Resolve existing managed links and file conflicts explicitly before applying dotfiles with Stow.
3. Organize the remaining Nix configuration into base, host, user, and feature aspects.
4. Remove unused inputs, assets, and tooling references. Preserve `system.stateVersion`.
5. Run repository validation, build `tpx1`, activate it, and verify a fresh login, networking, the desktop, and essential applications.
6. Add a small bootstrap script to clone [pszponder/dotfiles](https://github.com/pszponder/dotfiles) over HTTPS and run `just stow` as the regular user. Provide Git, Just, and Stow through Nix; reuse an existing checkout without automatically pulling updates. Keep bootstrap separate from system activation.

## Bootstrap implementation

The local Stow checkout is `/home/piotr/repos/github/pszponder/stow-dotfiles`, with origin `pszponder/dotfiles`. Bootstrap defaults to `~/repos/github/pszponder/stow-dotfiles`, clones over HTTPS if absent, and runs its `just stow` recipe. It requires the Stow layout and does not pull updates automatically.
